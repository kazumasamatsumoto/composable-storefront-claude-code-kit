# 文書の書き方

## 1. 型を選ぶ(templates/ の下)
| 頼まれたこと | 型 | 置き場所の例 |
|---|---|---|
| 担当を替わる、人に渡す | [引き継ぎ資料](templates/handover.md) | `docs/handover/<領域>.md` |
| 機能をどう作るか書く | [機能の設計書](templates/design.md) | `docs/design/<機能>.md` |
| 運用の作業や障害対応の手順 | [手順書](templates/runbook.md) | `docs/runbooks/<作業>.md` |
| OCC の API を説明する | [API 仕様(1 本 1 節)](templates/api.md) | `docs/api/<API>.md` |
| 仕組みを、知らない人に説明する | [説明資料](templates/explainer.md) | `docs/explain/<題>.md` |
| PowerPoint や Excel の資料をまとめる | まず cs-office-transcribe で文字起こしし、[説明資料](templates/explainer.md)の「要約」の形で書く | `docs/summaries/<元の名前>.md` |

設計の決定そのもの(ADR)は cs-adr、リリースノートは cs-release-notes の型を使う。

## 2. 決まり(どの型でも)
1. **根拠の種類を書く。** 事実の文の末尾に、どれで確かめたかを付ける。
   - (実測): 自分で動かして確かめた。コマンドと結果を残す
   - (ソース): コードを読んだ。`path/to/file.ts:12-30` の形で場所を書く
   - (公式): 公式ドキュメント。ページの URL を書く
   - (推論): 上のどれでもなく、筋道から考えたこと
   - (未確認): 確かめていない、または確かめられなかったこと
   印の無い断定を書かない。推論と未確認は、読み手が判断できるよう本文で目立たせる。
2. **やさしい言葉で書く。** 冒頭の要約(3 行まで)には専門用語を使わない。用語は初めて出るところで 1 回だけ言い換える(例: Facade = 画面が呼ぶ窓口のクラス)。1 文に 1 つのことだけ書く。
3. **会議で言える 3 文**を、説明資料と引き継ぎ資料の最後に置く。そのまま読み上げられる文にする。
4. **API は HTTP の呼び出し 1 本につき 1 節。** 仕組みが似ていても、別の URL は別の節にする。
5. **処理の流れは 1 段 1 行。** 各段に「どのファイルの、どのクラスが、何に責任を持つか」を書く。名前を矢印で並べただけの図にしない。
6. **前提を書き換えない。** SSR あり、Angular と SAP Commerce(Spring)の標準構成、BFF なし(CLAUDE.md)。前提と違う案は文書に入れず、人に上げる。
7. **分からないことは空欄にせず、「(未確認)誰に何を聞くか」を書く。**
8. 日付は 2026-10-19 の形。「先週」「最近」と書かない。

## 3. 書く手順
1. 読み手(誰が、いつ、何のために読むか)を 1 行で決め、文書の先頭に書く。
2. 材料を集める: コード(Grep で場所を特定し、Read で確かめる)、既存の docs、Office の資料(cs-office-transcribe)、人から聞いたこと。
3. 型に沿って書く。根拠の印を付けながら書く(後から付けない)。
4. 下のチェックを通す。
5. 人に返すときは、(推論)と(未確認)の一覧を添える。

## 4. チェック
- [ ] 冒頭の要約に専門用語が無い
- [ ] 事実の文に根拠の印がある。(ソース)には行番号まである
- [ ] (推論)と(未確認)を一覧にした
- [ ] API は 1 本 1 節。流れの各段に責任を書いた
- [ ] 前提(SSR、標準構成、BFF なし)と食い違う記述が無い
- [ ] 秘密(パスワード、鍵、.env の値、個人情報)を書いていない
