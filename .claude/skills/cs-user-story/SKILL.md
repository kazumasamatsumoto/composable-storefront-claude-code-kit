# ユーザーストーリーと受入条件

## 書式
```
ID: CS-123
ストーリー: <誰>として、<何>をしたい。なぜなら<理由>。
背景: 1〜3 行。現状の困りごと
実現手段の仕分け: 標準設定 / CMS / ストアフロントのコード / OCC・Commerce 側 / 外部連携(要確認を含む)
受入条件:
  AC1 Given <前提> When <操作> Then <結果>
  AC2 ...(境界: 0 件、上限、未ログイン、エラー)
計測: <KPI> を <どこで> 測り、<目標値>
優先順位の根拠: 影響する利用者 / 売上 / 法令 / 期限
制約: Public Cloud の制約(同期受注管理が非対応、など)、依存する他チーム
```

## チェック
- [ ] 受入条件は人がテストできる文になっている(「使いやすい」など曖昧語が無い)
- [ ] 境界ケースが最低 1 つある
- [ ] 実現手段に「要確認」が残っていれば、誰に確認するか書いてある
- [ ] 画面の文言は利用者の言葉。内部の実装名が無い

## 受入条件からテストへ
- AC の番号を E2E テストのファイル名か describe 名に残す(cs-e2e-flow)
